# Sauce Demo — Playwright JS + BDD Framework with AI Self-Healing Locators

A professional end-to-end test automation framework for the Shopify storefront
**https://sauce-demo.myshopify.com/**, covering the **Home**, **Login**, and
**Signup** pages.

Built with:

- **[Playwright](https://playwright.dev/)** (JavaScript) — browser automation & runner
- **[playwright-bdd](https://vitalets.github.io/playwright-bdd/)** — Cucumber/Gherkin `.feature` files on top of the Playwright runner
- **Page Object Model** — one page object per screen
- **AI Self-Healing Locators** — every element carries 2–3 fallback locators, and if they all fail at runtime a free AI model proposes a fresh selector
- **Self-Healing JSON Reports** — every heal is recorded to `reports/healing/`

---

## 1. Quick start

```bash
# 1. Install dependencies
npm install

# 2. Install the browser (Chromium)
npx playwright install chromium

# 3. (Optional) enable AI healing — copy env template and add a free API key
cp .env.example .env
#   then edit .env and set AI_API_KEY=...   (see "AI healing" below)

# 4. Run the whole suite
npm test

# 5. Open the HTML report
npm run report
```

> `npm test` automatically runs `bddgen` first (via the `pretest` hook) to compile
> `.feature` files into runnable specs under `tests/` (mirroring the `features/`
> sub-folders). If you ever call `npx playwright test` directly, run `npx bddgen`
> first. The `tests/` directory is generated and gitignored — never edit it by hand.

### Useful scripts

| Command                    | Description                                          |
| -------------------------- | ---------------------------------------------------- |
| `npm test`                 | Generate specs + run the full suite                  |
| `npm run test:headed`      | Run with a visible browser                           |
| `npm run test:smoke`       | Run only `@smoke` scenarios (critical path, 3)       |
| `npm run test:sanity`      | Run only `@sanity` scenarios (key flows, 7)          |
| `npm run test:regression`  | Run only `@regression` scenarios (everything, 11)    |
| `npm run test:login`       | Run only `@login` scenarios                          |
| `npm run test:signup`      | Run only `@signup` scenarios                         |
| `npm run test:home`        | Run only `@home` scenarios                           |
| `npm run test:debug`       | Run under the Playwright Inspector                   |
| `npm run typecheck`        | Type-check the JS sources (`tsc` on `// @ts-check`)  |
| `npm run report`           | Open the last Playwright HTML report                 |
| `npm run allure:serve`     | Generate + open the Allure report in one step        |
| `npm run allure:generate`  | Render `allure-results/` → static `allure-report/`   |
| `npm run allure:open`      | Open a previously generated Allure report            |
| `npm run healing:report`   | Print a summary of the last self-healing report      |

### Test tiers (tags)

Scenarios are tagged so CI can run the right depth at the right time:

| Tag           | Count | When to run                                             |
| ------------- | ----- | ------------------------------------------------------- |
| `@smoke`      | 3     | Every commit / PR — critical "does it load" checks.     |
| `@sanity`     | 7     | Post-merge — smoke + core flows & key negative cases.   |
| `@regression` | 11    | Nightly / release — the full suite.                     |

Tags stack (a scenario can be `@smoke @sanity`), and the area tags
(`@home`/`@login`/`@signup`) still work for slicing by feature.

## 3. How the self-healing locators work

Every UI element is declared as an **element definition** — a logical name, a
plain-language description, and an **ordered list of 2–3 candidate locators**:

```js
emailInput: {
  name: 'Login email input',
  description: 'Email address text box on the customer login form',
  locators: [
    { by: 'id',  value: 'customer_email' },                    // primary
    { by: 'css', value: 'input[name="customer[email]"]' },     // fallback 1
    { by: 'css', value: '#customer_login input[type="email"]' } // fallback 2
  ],
}
```

At runtime, `SelfHealingLocator.resolve()` applies a **three-layer strategy**:

1. **Primary locator** — the happy path. If it resolves, nothing is reported.
2. **Static fallbacks** — tried in order. The first that works "heals" the
   element and the event is recorded.
3. **AI healing** — if *all* static locators fail and AI healing is enabled, a
   pruned snapshot of the live DOM plus the element's description are sent to a
   free AI model, which returns a fresh CSS/XPath selector. If that selector
   works, the heal is recorded with the provider/model used.

If every layer fails, a rich error is thrown listing everything that was tried.

Supported locator strategies: `id`, `css`, `xpath`, `role`, `text`,
`placeholder`, `label`, `testid`, `altText`.

### Self-healing reports

Any heal beyond the primary locator is written to **`reports/healing/`**:

- `latest.json` — the most recent run (easy for CI to pick up)
- `healing-report-<timestamp>.json` — full history

Each event captures the page, element, failed primary, the healed locator, the
strategy (`fallback` or `ai`), and — for AI heals — the provider and model.
Heals are also printed live during the run:

```
🩹 FALLBACK-HEALED [LoginPage › Login email input] "id=customer_email" → "css=input[name=\"customer[email]\"]"
🤖 AI-HEALED       [HomePage › Cart link]          "css=a[href=\"/cart\"]" → "css=header .cart-icon" (via gemini/gemini-2.0-flash)
```

## 4. AI healing configuration

AI healing is **optional**. Without an API key the framework simply relies on
the static fallback locators (and logs a warning if it ever needed the AI).

Configure via `.env` (copy from `.env.example`):

| Variable              | Default    | Notes                                                       |
| --------------------- | ---------- | ----------------------------------------------------------- |
| `AI_HEALING_ENABLED`  | `true`     | Master switch. Set `false` to disable AI calls entirely.    |
| `AI_PROVIDER`         | `gemini`   | `gemini` \| `groq` \| `openrouter` — all have free tiers.   |
| `AI_API_KEY`          | *(empty)*  | Key for the chosen provider. Empty = AI healing skipped.    |
| `AI_MODEL`            | per-provider | Optional model override.                                  |

Get a **free** API key:

- **Gemini** (default) — https://aistudio.google.com/apikey
- **Groq** — https://console.groq.com
- **OpenRouter** (use a `:free` model) — https://openrouter.ai/keys

All three are called through the same OpenAI-compatible `/chat/completions`
contract, so switching providers is just an env change.

## 5. What is covered

| Area   | Scenarios                                                                       |
| ------ | ------------------------------------------------------------------------------- |
| Home   | Page loads with products; header controls visible; navigation to login/register |
| Login  | Login form loads; invalid credentials are rejected (user stays unauthenticated) |
| Signup | Registration form loads; too-short password and blank email are rejected        |

> **Note on negative cases:** the storefront's login and registration forms are
> protected by **hCaptcha**, which suppresses the classic inline error banners
> for automated submissions. The negative scenarios therefore assert that the
> user is **not authenticated / remains on the form page** (a deterministic,
> honest signal) rather than scraping for an error message that hCaptcha hides.

## 6. Reporting

Three report layers are produced on every run:

- **Playwright HTML** — `reports/html/` (`npm run report`).
- **Allure** — rich, history-aware reporting.
  ```bash
  npm test                 # produces allure-results/
  npm run allure:generate  # renders allure-results/ -> allure-report/
  npm run allure:open      # open it
  # or, in one shot:
  npm run allure:serve
  ```
  Allure requires a JDK (Java 8+) on the machine generating the report. Test
  metadata (tags, steps, screenshots/traces on failure) flows through
  automatically; environment info is set in `playwright.config.js`.
- **Self-healing JSON** — `reports/healing/` (see §3).

## 7. SonarQube / SonarCloud

Static analysis is configured in `sonar-project.properties` (project key,
source layout, exclusions for generated/report folders).

```bash
# Requires the sonar-scanner CLI and a running SonarQube (or SonarCloud) server.
export SONAR_HOST_URL=https://your-sonarqube
export SONAR_TOKEN=xxxxxxxx
sonar-scanner
```

In CI this runs from the Jenkinsfile's **SonarQube Analysis** stage followed by
a **Quality Gate** check that fails the build if the gate is red.

## 8. CI/CD (Jenkins)

`Jenkinsfile` is a declarative pipeline with these stages: Checkout → Install →
Type check → Generate BDD specs → Run tests → SonarQube Analysis → Quality Gate,
and a `post` block that publishes the **Allure report**, archives artifacts and
prints the self-healing summary.

- **Parameter `SUITE`** — `regression` (default) / `smoke` / `sanity` / `all`.
- **Parameter `AI_HEALING`** — when enabled, the `ai-api-key` credential is
  injected as `AI_API_KEY` for the run (off by default for deterministic CI).
- **Required Jenkins tools/plugins** (configure once, names referenced in the
  file): NodeJS plugin (`NodeJS-20`), SonarQube Scanner plugin (server
  `SonarQube`, scanner tool `SonarScanner`), and the Allure plugin (tool
  `Allure`). AnsiColor + Timestamper plugins are used for nicer logs.

## 9. Configuration knobs

- **Base URL / headless** — `BASE_URL`, `HEADLESS` env vars (see `.env.example`).
- **Candidate timeout** — `HEAL_CANDIDATE_TIMEOUT` (ms) controls how long each
  locator candidate is tried before moving to the next. Default `3500`.
- **Browsers** — Chromium is enabled by default; uncomment Firefox/WebKit in
  `playwright.config.js` to broaden coverage.

## 10. Requirements

- Node.js 18+ (developed on Node 20)
- Pinned: `@playwright/test@1.55.0`, `playwright-bdd@8.3.1`
  (these versions are compatible; newer Playwright 1.61 currently breaks
  playwright-bdd's ESM loader).
- **Java 8+** — only to *generate* the Allure report locally (`allure:*` scripts).
- **CI extras** — a SonarQube/SonarCloud server + `sonar-scanner` for analysis;
  Jenkins with the NodeJS, SonarQube Scanner and Allure plugins for the pipeline.
